# 打包运行执行说明

> 说明：本文件基于当前 `DEPLOY/` 与仓库结构编写；后续将整合入 `运行指南.md`。

## 环境要求

| 组件                     | 版本要求 | 说明                                             |
| ------------------------ | -------- | ------------------------------------------------ |
| Docker                   | 24+      | 安装后确认 `docker compose` 命令可用（V2 版本） |
| NVIDIA Container Toolkit | 可选     | 仅 GPU 机器需要，WSL2 环境自带支持               |
| 宿主机显卡驱动           | 可选     | GPU 直通需要 NVIDIA 驱动                         |

> 本方案为 **Docker 全栈部署，无需本地 conda / Python / Node**——依赖已打进后端镜像（`backend/requirements.txt`）与前端镜像（`frontend/package.json`）。

### WSL2 用户注意

WSL2 内安装 NVIDIA 驱动后自带 container 支持，无需额外配置 `nvidia-container-toolkit`。确认方式：

```bash
# 在 WSL2 内执行，确认能看到 GPU 信息
nvidia-smi
```

> 如果暂时不用 GPU，直接不加 `-f DEPLOY/docker-compose.gpu.yml` 参数即可，**无需任何额外配置**。

## 服务架构（docker-compose.yml 全栈 7 服务）

| 服务 | 说明 | 端口 |
| --- | --- | --- |
| **backend** | FastAPI（后端镜像，含 MCP 子进程/模型 + **小说解构模块**） | 8000 |
| **frontend** | Nginx（前端镜像，/api 反向代理 + SSE） | 80 |
| **mysql** | MySQL 8.0（容器名固定 `006gaizao-mysql`） | 3306 |
| **milvus** | 向量检索引擎（Milvus Standalone） | 19530 |
| **etcd** | Milvus 元数据存储 | — |
| **minio** | 向量数据文件存储 | — |
| **attu** | Milvus 可视化面板 | 3000 |

Milvus Standalone 由三个独立服务组成，**版本必须与存量数据完全一致**，否则无法加载已有向量数据：

| 服务 | 镜像 | 版本 | 作用 |
| --- | --- | --- | --- |
| **milvus** | `milvusdb/milvus` | v2.6.19 | 向量检索引擎 |
| **etcd** | `quay.io/coreos/etcd` | v3.5.25 | 元数据存储 |
| **minio** | `minio/minio` | RELEASE.2024-12-18 | 向量数据文件存储 |
| **attu** | `zilliz/attu` | latest | 可视化面板（可选） |

> ⚠️ **禁止随意升级 Milvus 镜像版本！** 版本不一致直接导致无法读取旧向量数据。`docker compose down` 时**禁止加 `-v` 参数**，否则会永久删除持久化数据卷。

## 首次部署完整流程

### 第 1 步：准备 `.env` 文件

```bash
cp backend/src/.env.example backend/src/.env
```

编辑 `backend/src/.env`，至少填写：

- `DeepSeek_API_KEY` —— LLM 调用密钥
- `MYSQL_PASSWORD` / `MYSQL_ROOT_PASSWORD` —— MySQL 业务库/root 密码（必须修改占位符）
- `JWT_SECRET` —— 建议 32 位以上随机串

> **小说解构（可选）**：`NOVEL_*` / `DECONSTRUCT_*` 变量有默认值、**开箱即用**；解构仅需 MySQL + DeepSeek（复用同一把 `DeepSeek_API_KEY`），**不依赖 Milvus / GPU**。需要调并发、切分阈值、超时或开启 validator 时才改。

**关键：首次部署保持联网下载模型**（`HF_HUB_OFFLINE` 置 `0`，`.env.example` 中该行默认注释，即为在线；勿在首次置 1）。

> `SEED_DOCS_ENABLED` 由 compose 强制为 `1`，启动会自动初始化内置测试数据（见下）。

### 第 2 步：构建镜像

在仓库根目录执行（如 `.../006gaizao`）：

```bash
# 无 GPU
docker compose -f DEPLOY/docker-compose.yml build

# 有 GPU
docker compose -f DEPLOY/docker-compose.yml -f DEPLOY/docker-compose.gpu.yml build
```

> 后端首次构建需拉取 torch 等大依赖（含 CUDA 轮子），耗时较长属正常；前端构建使用 `frontend/` 目录（多阶段 Nginx）。

### 第 3 步：启动服务

```bash
# 无 GPU 机器
docker compose -f DEPLOY/docker-compose.yml up -d

# 有 GPU 机器
docker compose -f DEPLOY/docker-compose.yml -f DEPLOY/docker-compose.gpu.yml up -d
```

### 第 4 步：确认模型下载完成

```bash
# 观察后端日志
docker compose -f DEPLOY/docker-compose.yml logs -f backend
```

等待看到以下输出（表示 Embedding + Reranker 模型加载完成）：

```
Model loading complete
✅ 服务依赖初始化完成
```

> 此时**内置测试数据会自动初始化**：demo 账号 `12345678910 / 1234567` 可直接登录前端，知识库中已有「示例知识库」（3 份示例文档）。

### 第 5 步：开启离线模式（可选）

模型缓存到 `huggingface_cache` 卷后，可恢复离线模式避免每次联网检查：

```bash
# 编辑 backend/src/.env，取消注释：
HF_HUB_OFFLINE=1

# 重启后端使配置生效
docker compose -f DEPLOY/docker-compose.yml restart backend
```

## 存量数据迁移

如果你已有旧 Milvus 向量数据（从之前的 `milvus-standalone` 等容器），按以下步骤迁移：

### 1. 确认旧容器数据卷路径

```bash
docker inspect milvus-etcd | grep -A5 Mounts
docker inspect milvus-minio | grep -A5 Mounts
docker inspect milvus-standalone | grep -A5 Mounts
```

### 2. 将旧数据复制到新 volume

```bash
# 创建新 volume（如果已有则跳过）
docker volume create --name deploy_etcd_data
docker volume create --name deploy_minio_data
docker volume create --name deploy_milvus_data
```

```bash
# 迁移 etcd 数据
docker run --rm -v milvus-etcd-data:/source -v deploy_etcd_data:/target alpine \
    cp -a /source/. /target/

# 迁移 minio 数据
docker run --rm -v milvus-minio-data:/source -v deploy_minio_data:/target alpine \
    cp -a /source/. /target/

# 迁移 milvus 数据
docker run --rm -v milvus-standalone-data:/source -v deploy_milvus_data:/target alpine \
    cp -a /source/. /target/
```

> `milvus-etcd-data`、`milvus-minio-data`、`milvus-standalone-data` 为旧容器数据卷名称，请根据第 1 步的实际输出替换。

### 3. 验证数据完整性

```bash
docker compose -f DEPLOY/docker-compose.milvus-only.yml up -d
# 用本地 Python 验证
python -c "
from pymilvus import connections, utility
connections.connect(host='127.0.0.1')
print('集合列表:', utility.list_collections())
"
```

### 4. 启动完整集群

确认数据加载正常后，启动全服务：

```bash
docker compose -f DEPLOY/docker-compose.yml up -d
```

## 日常使用命令

### 启动

```bash
# 有 GPU
docker compose -f DEPLOY/docker-compose.yml -f DEPLOY/docker-compose.gpu.yml up -d

# 无 GPU
docker compose -f DEPLOY/docker-compose.yml up -d
```

### 停止

```bash
docker compose -f DEPLOY/docker-compose.yml down
```

> `down` 会停止并删除容器，但不会删除 `milvus_data`、`etcd_data`、`minio_data`、`huggingface_cache`、`mysql_data` 数据卷。

### 查看日志

```bash
# 所有服务
docker compose -f DEPLOY/docker-compose.yml logs -f

# 只关注后端（推荐：带时间戳 + 最近 100 行）
docker compose -f DEPLOY/docker-compose.yml logs --tail 100 -f backend

# 只关注 Milvus
docker compose -f DEPLOY/docker-compose.yml logs -f milvus

# 调试模式下的向量库日志
docker compose -f DEPLOY/docker-compose.milvus-only.yml logs -f milvus
```

> 容器名随 compose 项目名变化（在仓库根运行则前缀为 `006gaizao-*`，如 `006gaizao-backend-1`）；MySQL 因 `container_name` 固定为 `006gaizao-mysql`。建议始终用 `docker compose ... logs <service>` 而非裸 `docker logs <容器名>`。

### 重启单个服务

```bash
docker compose -f DEPLOY/docker-compose.yml restart backend
```

### 重建镜像（依赖变动时）

```bash
docker compose -f DEPLOY/docker-compose.yml build --no-cache backend
docker compose -f DEPLOY/docker-compose.yml up -d
```

## 部署后使用小说解构

1. **上传小说**：在「知识库管理」上传小说文件（.txt/.md），上传时带 `deconstruct=1`（或到工作台手动触发）。
2. **解构工作台**：`/deconstruct`，左书列选书 → 5 tab——**解构**（任务列表/SSE 实时进度/失败章重试）、**复核**（一致性校验待办 + 原文证据分屏裁决）、**图谱**（1-hop 关系图 + 章节滑块时态回放）、**百科**（实体卡 L0-L4：基线/弧光/伏笔规则/明暗 + 快照时间轴 + 热力图）、**数据**（10 类结构化数据浏览）。
3. **数据落库**：解构产物写入 MySQL 15 张解构表（entity/entity_snapshot/timeline_event/foreshadowing/rule_check 等）；跨章一致性校验可疑项进 `validation_issue` 待复核。
4. 详细业务流见 `docs/业务流程说明.md` §6；架构见 `docs/AI架构设计.md` §17-26。

> 解构仅需 MySQL + DeepSeek，**无需 Milvus / GPU**；`NOVEL_*`/`DECONSTRUCT_*` 环境变量默认即可运行（见首次部署说明）。

## 常见问题排查

### Q：启动后后端日志显示 `Connection refused` 连接 Milvus

Milvus 首次启动需要初始化数据（约 30-60 秒）。`depends_on: condition: service_healthy` 会自动等待。如果超时：

```bash
# 单独检查 Milvus 状态
docker compose -f DEPLOY/docker-compose.yml exec milvus python3 -c "import urllib.request; urllib.request.urlopen('http://localhost:9091/healthz')"
```

### Q：`torch.cuda.is_available()` 返回 `False`

确认链路：

```bash
# 1. 宿主机 GPU 驱动
nvidia-smi

# 2. Docker GPU 运行时
docker compose -f DEPLOY/docker-compose.yml -f DEPLOY/docker-compose.gpu.yml run backend nvidia-smi

# 3. PyTorch 检测
docker compose -f DEPLOY/docker-compose.yml -f DEPLOY/docker-compose.gpu.yml run backend python -c "import torch; print(torch.cuda.is_available())"
```

### Q：模型加载失败/下载超时

检查 HuggingFace 网络连通性：

```bash
# 临时关闭离线模式测试
docker compose -f DEPLOY/docker-compose.yml exec backend python -c "from huggingface_hub import list_models; print('OK')"
```

如果网络受限，可手动下载模型到 `huggingface_cache` 卷：

```bash
# 在宿主机下载（假设已有缓存）；BACKEND=$(docker compose -f DEPLOY/docker-compose.yml ps -q backend)
docker cp ~/.cache/huggingface/hub $(docker compose -f DEPLOY/docker-compose.yml ps -q backend):/root/.cache/huggingface/
```

### Q：前端页面空白 / API 请求 502

确认 Nginx 能到达后端：

```bash
docker compose -f DEPLOY/docker-compose.yml exec frontend wget --spider http://backend:8000/api/health
```

### Q：`docker compose down -v` 会怎样？

**会永久删除所有持久化数据卷**（`milvus_data`、`etcd_data`、`minio_data`、`huggingface_cache`、`mysql_data`），包括已入库的向量集合、下载的模型缓存与数据库数据。**永远不要在生产/有存量数据的环境执行 `down -v`**。

```bash
# 安全停止（保留数据卷）
docker compose -f DEPLOY/docker-compose.yml down

# ❌ 危险！以下命令会删除所有数据
docker compose -f DEPLOY/docker-compose.yml down -v
```

### Q：`docker compose` 命令报错（Compose V1 vs V2）

本项目使用 Compose V2（`docker compose`，中间有空格）。如果使用旧版 `docker-compose`（带横线），`condition: service_healthy` 会被忽略：

```bash
# 正确
docker compose -f DEPLOY/docker-compose.yml up -d

# 错误（V1 不支持 service_healthy）
docker-compose -f DEPLOY/docker-compose.yml up -d
```
